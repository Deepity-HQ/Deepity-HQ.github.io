Detailed Description

Declares the Google Highway (github.com/google/highway) runtime- dispatched implementations backing a handful of CPUBackend's elementwise kernels. Deliberately a separate CMake target (DeepityHighwayKernels, see CMakeLists.txt) compiled WITHOUT the project's hard-pinned -march flag – Highway's own foreach_target.h mechanism compiles multiple per-ISA-target variants of CPUBackendHighway.cpp and picks the best one at runtime; a project-wide fixed ISA would defeat that entirely.

The *F16Dispatch functions below are the exception: they're the ONLY genuinely Highway-lane-vectorized path for hwy::float16_t anywhere in CPUBackendT (issue #50) – every other CPUBackendT<T, AccumT> elementwise kernel, for every T other than float/double, falls back to a plain scalar hwy::ConvertScalarTo<AccumT>(...) loop (see CPUBackendT.cpp's own comments on that generic "Bucket C" wrap). These four promote each f16 lane group to a same-width float lane group (via Highway's PromoteTo, backed by the hardware VCVTPH2PS instruction on this machine's f16c-capable AVX2 target), reuse the EXISTING ActivationForwardHwy/ ActivationDerivFromPreactHwy templates below bit-for-bit (same vectorized math already proven correct for the float/float path), and demote back (VCVTPS2PH) only where the destination is actually T=hwy::float16_t – the AccumT-output variant skips that step entirely, since AccumT=float needs no demotion.
